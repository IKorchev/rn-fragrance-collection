## Project overview

A React Native (Expo) mobile app for tracking a personal fragrance/perfume collection. Users sign in with Google or Apple, search a fragrance catalog (or add a fragrance manually if the catalog doesn't have it), add items to their collection, track how many times they've worn each one, and use a weighted-random "picker" to choose what to wear. Auth and app data live in Supabase (Postgres + Supabase Auth, with Row Level Security guarding per-user rows) — the same Supabase project as the standalone `fragrance-db` catalog repo. Search queries the `fragrances` catalog table directly via the `search_fragrances` Postgres RPC (live debounced search plus a brand filter), and items added from search or the Most Worn leaderboard populate `user_fragrances.fragrance_id`, the FK to the canonical catalog row. **The catalog table itself is name/brand/image only** (plus `image_url` — our own R2 CDN — and `source_url`, a dedup key). Community opinion data lives in separate user-keyed tables beside it: `fragrance_ratings` (one 1–5 star rating per user per catalog fragrance — this *is* the personal rating for catalog-linked bottles; its average/count shows as "★ 4.2 (56)" on search/leaderboard rows and the detail sheet via the batched `get_fragrance_ratings` RPC; manual adds have no `fragrance_id`, so their rating falls back to `user_fragrances.rating`, and `src/lib/utils/use-rated-collection.ts` resolves the two) and `fragrance_votes` (`src/components/fragrance-voting.tsx` on the detail sheet: 1–2 seasons, gender female/unisex/male, sillage and longevity 1–5; own-rows RLS, aggregates only via the `get_fragrance_vote_summary` RPC). Personal per-item `notes` stay on `user_fragrances`. **Open product question — flagged for the user, don't resolve it yourself:** the long-standing rule was "don't add catalog notes/rating/gender features", and the shipped community ratings and voting contradict it. Until the user decides, don't extend community catalog metadata further (no scent notes, no new vote dimensions) and don't remove what exists.

Discover (the app's landing tab, `(discover)/index.tsx`) puts two views behind an iOS `SegmentedControl` under its large title. **Top** (`src/components/discover-top.tsx`, the default — populated for everyone) picks between two community rankings from a `NativeMenu` dropdown (with a period dropdown beside it for the first): the "Most Worn" top-100 leaderboard computed from real wear data (`wear_events` + the `top_worn_fragrances` SECURITY DEFINER RPC, windowed day/week/month/year/all, `EXECUTE` revoked from `anon`) and the Collectors leaderboard (public `user_profiles` ranked by `total_wears`; rows push `user-profile.tsx`). **For You** (`src/components/discover-for-you.tsx`, empty until the user has a collection to base it on) is powered by one `recommend_fragrances` SECURITY DEFINER RPC: candidate generation, owned-item exclusion, scoring, explanations, and diversification stay in Postgres; `fragrance_community_stats` is maintained incrementally by wear/rating triggers and indexed for popularity and preferred-brand candidate reads, so recommendation requests never aggregate raw event rows. **Search** is its own bottom tab (`(search)/index.tsx`, `role="search"` so iOS 26 renders it as the tab bar's separate search button): the catalog search plus the manual-add entry point. Before anything is typed, Search shows browse sections (`src/components/search-browse.tsx`): trending (`top_worn_fragrances`, this week falling back to all time), popular brands (`popular_brands`, a SECURITY DEFINER RPC ranking catalog brands by distinct collectors who own or wishlist them, once at least 3 do — it returns only brand names and catalog sizes — topped up from the `FEATURED_BRANDS` list in `queries.ts`; tapping one applies the brand filter), and Explore (`discover_fragrances`, a random slice that skips imageless rows).

User-suggested catalog additions: a manual add (brand + name in `src/components/manual-add-modal.tsx`) goes through the `add_manual_fragrance` RPC, which inserts the personal row (`user_fragrances`, `fragrance_id` null) and silently queues a `fragrance_submissions` row in one transaction (the suggestion half is a best-effort subtransaction — it can never fail or delay the add; no user-facing toggle — surfacing to the shared catalog is a moderator decision, not the submitter's; rate-capped at 5 pending/user, serialized via advisory lock; stores a pg_trgm similarity score + closest catalog match for triage, found via KNN on the `fragrances_brand_name_trgm_gist_idx` GiST index). The modal also shows a live "did you mean" strip (reuses `useFragranceSearch`) so near-misses become catalog-linked adds instead of submissions. Pending submissions are invisible to other users — only the `review_submission` RPC (moderator-gated via the `moderators` table, or trusted when called with no JWT from the Supabase dashboard SQL editor: `SELECT review_submission('<id>', 'approve'|'merge'|'reject', ...)`) inserts the `fragrances` catalog row (approve, with `source_url = 'user:<submission-id>'` as the dedup key) or links an existing one (merge), backfilling the submitter's `fragrance_id` + `wear_events`. Reject leaves the personal row untouched; the submitter gets a push for either decision (`supabase/functions/notify-submission-decision`, fired best-effort from `review_submission` via pg_net). Moderators work the queue in-app in `src/app/moderation.tsx` (Profile-tab entry gated on `useIsModerator`), but authorization lives in the RPCs, not UI visibility. Corrections to an *existing* catalog row (wrong image, duplicate, wrong name/brand) are a separate flow: the detail sheet's "Report an issue" link opens `src/app/report-fragrance.tsx` (`submit_fragrance_report` → `fragrance_reports`, triaged in the same moderation screen; the data fix itself is still a manual SQL step). See the `catalog-submissions` skill.

Gamification (`src/lib/gamification/`) is a pure, deterministic core — no I/O and no stored state; everything is a pure function of wear history, the collection snapshot, and an explicit `now`, so it always replays the same from the data. It covers the wear streak (device-local days, same semantics as the one-wear-per-day cap) and badges (`badges.ts`; full wall at `src/app/badges.tsx`, a 3-badge preview on Profile via `src/lib/utils/badge-highlights.ts`). XP/levels and weekly quests were removed on purpose (three overlapping progress systems on top of a simple core loop) — don't reintroduce them; `user_profiles.level`/`xp` survive only because 1.3.x binaries still write them, and nothing reads them. Screens read it through `useGamification()` (`src/lib/utils/use-gamification.ts`, which also folds in Streak Saver freeze dates), never `computeGamification` directly. `(tabs)/_layout.tsx` mounts the session-wide side effects once: badge-unlock toasts (`use-gamification-alerts.ts`, at most one per app session against an AsyncStorage last-seen snapshot); `useStreakSaver()` (on app open, a just-broken streak of ≥3 days is auto-repaired for Pro users via the `use_streak_save` RPC — `streak_saves`, 2 per calendar month, last 3 days only, all enforced server-side — while free users get a one-time upsell per distinct break); and `useProfileSync()`. Other engagement surfaces: the "Getting started" onboarding checklist (`src/components/onboarding-checklist.tsx` + `use-onboarding.ts`; steps derived from real collection state, shown on the Collection and Search empty states, resumable from Profile), a GitHub-style wear heatmap on Profile (`src/components/wear-heatmap.tsx`), and a monthly recap (`src/app/monthly-recap.tsx`, a fullScreenModal computed client-side from the wear diary; `use-monthly-recap-prompt.ts` offers it by toast once, in the first week of a new month).

Public profiles are opt-in (`user_profiles`, private by default; the Profile tab's public toggle creates the row). The row is a client-pushed snapshot of the client-computed gamification state (streak, badge ids, counts, plus display name and avatar) — the server never recomputes it, so it's display/leaderboard data, not an integrity boundary; `src/lib/utils/use-profile-sync.ts` keeps it fresh while public. Real per-user wear data for a profile comes only from the `user_top_worn` SECURITY DEFINER RPC; the collection list, notes, ratings, and wear diary are never exposed. Owners can set a collection header photo behind their avatar (`src/components/profile-hero.tsx`, `src/lib/profile-header-photo.ts`): the only write path into the `profile-headers` bucket is the `upload-header-photo` edge function, which NSFW-scans the image and fails closed (`reason: "rejected"`) before storing it and updating `header_image_path`; the `guard_user_profile_writes` trigger stops clients from setting that path or `moderation_hidden_at` themselves.

Sharing: every share entry point (detail sheet, today's scent on Profile, picker result, monthly recap) builds its text in `src/lib/share.ts` and goes through `src/components/share-sheet-modal.tsx`, which always previews the exact text before `Share.share()` and makes personal data (times worn, rating) an explicit opt-in toggle.

Wishlist and bottle status: `wishlist_items` (catalog-only, own-rows RLS; name/image come through the `fragrances` embed, not a snapshot) backs the "Want to try" toggle on the detail sheet of any catalog fragrance the user doesn't own, next to an "Add to collection" button; `src/app/wishlist.tsx` (pushed from Profile's Activity group) lists it, with Add moving an item into the collection and off the wishlist (`addFragranceToCollection` resolves `true` on success for exactly this). Hooks: `useWishlist`/`useWishlistToggle` (optimistic). Collection rows carry `bottle_type` (`full`/`decant`/`sample`, nullable) and `running_low`, edited in the detail sheet's Bottle section and shown on the row's subtitle (decants/samples and running low only — a full bottle is the unremarkable default). A home-screen quick action ("Pick for me" → `/picker`, `expo-quick-actions`, native module) is registered by `src/lib/utils/use-quick-actions.ts` from the tabs layout while the collection is non-empty, and cleared on sign-out.

Public-profile report and block (App Review 1.2 for the Collectors / `user-profile.tsx` UGC surface): the user-profile header's overflow menu (hidden on your own profile) opens `src/app/report-profile.tsx` (`submit_profile_report` — four reasons + optional details, 20-pending cap surfaced via `isTooManyReportsError`) or blocks the user (`user_blocks` insert, then back + invalidate `top-collectors`/`public-profile`/`user-top-worn`). Blocks are enforced server-side — the `user_profiles` SELECT policy and `user_top_worn` treat a blocked user as private — so RLS also hides the blocked profile from the blocker; the Blocked users list (`src/app/blocked-users.tsx`, Profile-tab row shown only while blocks exist) therefore shows a device-local name/avatar snapshot taken at block time (`src/lib/blocked-user-labels.ts`). Moderators triage reports in `moderation.tsx`'s Profiles tab: Hide (`review_profile_report` forces private, stamps `moderation_hidden_at` so a trigger refuses re-publishing, settles all pending reports for that profile, and returns the cleared header path, which `AuthContext.reviewProfileReport` removes from the `profile-headers` bucket via the Storage API) or Dismiss.

Release-readiness pieces live alongside the core app: `supabase/functions/delete-account` (in-app account deletion, invoked from the profile screen — required by both app stores), a daily wear-reminder push with a per-device opt-out (`user_push_tokens.reminders_enabled`, toggled on the Settings screen; the OS permission prompt is never shown at launch — iOS only ever shows it once — so it's offered once after the first logged wear via `offerDailyReminderOnce` in `src/lib/notifications.ts`, or from that toggle), and `docs/privacy-policy.md` (host publicly and link from both store listings). Personal-data export (`src/app/export-data.tsx`, Settings entry point; collection incl. bottle status, diary, wishlist, votes) writes a real temporary `.csv`/`.json` file to a `data-exports` subdirectory under the OS-reclaimable cache dir (`expo-file-system`'s `File`/`Directory`/`Paths` API, not the deprecated `expo-file-system/legacy` one) and hands it to the OS share sheet with the matching MIME type/UTI (`expo-sharing`'s `Sharing.shareAsync`) — cleanup runs before the *next* export rather than right after the current one, since `shareAsync`'s promise resolves once the share intent is launched on Android, not once the receiving app finishes reading the file. Both `expo-file-system` and `expo-sharing` are native modules (added via `expo install`) and require a dev-client rebuild after a fresh checkout, same as the monetization modules below — `version` in app.json was bumped accordingly when they were added.

Observability: `src/lib/sentry.ts` is fully inert (no init, no native calls) until `EXPO_PUBLIC_SENTRY_DSN` is set. When it is, `initSentry()` (called once at the top of `_layout.tsx`, before `Sentry.wrap`) sets `environment` (`development`/`production`, override via `EXPO_PUBLIC_SENTRY_ENVIRONMENT`) and a `release`/`dist` derived from `app.json`'s `version` + the platform build number; `sendDefaultPii` stays `false` — no device name/IP/user email. `reportError(error, extra?)` is the one call every async catch should route through instead of `console.log`: it always logs in dev and reports to Sentry in prod. `extra` may only ever carry a small non-sensitive tag (e.g. `{ flow: "delete-account" }`) — never user-entered content (notes, ratings) or auth tokens. `Sentry.ErrorBoundary` wraps the entire provider tree in `_layout.tsx` regardless of whether a DSN is set (fallback: `src/components/app-crash-fallback.tsx`, deliberately independent of `useTheme`/any context, since the crash may have originated inside one of those providers) — it's a safety net on its own, not just a Sentry integration point. Release source-map upload goes through the official `@sentry/react-native/expo` config plugin (`app.json`, bare — no org/project baked in) plus `getSentryExpoConfig` (`metro.config.js`); `SENTRY_ORG`/`SENTRY_PROJECT`/`SENTRY_AUTH_TOKEN` are read from the EAS build environment, never committed. See `docs/sentry.md` for the dashboard/EAS setup this still needs.

Monetization: a RevenueCat Pro subscription (`src/lib/purchases.ts`, paywall entry on the profile screen; `isPro` lives on `AuthContext`, mirrored server-side in the `subscriptions` table that only the `revenuecat-webhook` edge function writes). The free/Pro boundary is documented at the top of `src/lib/entitlements.ts`: free keeps the whole core loop (unlimited wears/undo, tags, an unfiltered picker, the day-grouped wear diary) with a collection capped at `FREE_COLLECTION_LIMIT` (40 — enforced server-side by the `enforce_free_tier_collection_cap` trigger, whose `free_tier_collection_limit` error the client matches to show an upsell; the two numbers are kept in sync by hand); Pro adds an unlimited collection, picker filters (tag/brand/unworn — `src/components/picker-filter-sheet.tsx` + `src/lib/utils/picker-filters.ts`, applied as `AuthContext.pickerPool` without touching the weighting math), wear-history brand/tag filters and insights, Streak Saver, and no ads. Locked surfaces share `promptProUpsell`. Ads: an AdMob interstitial shown when the picker modal closes (`src/lib/ads.ts` — requested when the picker opens and shown from `picker.tsx`'s unmount cleanup only if the lever was pulled; frequency-capped in `ads.ts` in release builds — none in an account's first 3 days, then at most once per 12h, persisted in AsyncStorage; skipped for Pro users; dev builds always serve Google's test interstitial, release builds read `EXPO_PUBLIC_ADMOB_INTERSTITIAL_AD_UNIT_ID` from `.env.local`). RevenueCat Test Store keys (`test_…`, what `.env.local` and EAS currently hold) only work in debug builds — the SDK alerts and closes a release build configured with one — so `purchasesEnabled` is false in release builds until real App Store / Play Store keys replace them. Both native modules (`react-native-purchases`, `react-native-google-mobile-ads`) require a dev-client rebuild after a fresh checkout, and any change to them must bump `version` in app.json (runtimeVersion policy is appVersion — an OTA update reaching a binary without the native modules crashes at bundle eval). The real AdMob App ID is already in app.json's `react-native-google-mobile-ads` plugin block. UMP consent (GDPR/EEA) is handled: `initializeAds` runs `AdsConsent.gatherConsent()` from a root-layout mount effect (the form needs the Activity) and only starts the SDK when `canRequestAds` is true. **Before an iOS release**: give iOS its own AdMob App ID in that block (the Android app's id is currently used for both platforms) and add the ATT tracking prompt (iOS-only, not implemented — no iOS build exists yet).

OTA updates are **self-hosted** (xprem v3.2.6 on Cloud Run at `https://xprem-419723040511.europe-west1.run.app`, a private GCS bucket for bundles, and a dedicated Neon Postgres for the control plane), not EAS Update — `eas update` must never be run. `app.config.js` extends `app.json` and owns the `updates` block because the channel header must be a build-time literal and the dev-client code-signing guard needs JS; `app.json` keeps everything else including `runtimeVersion`. Publishing goes through `yarn ota:publish` (preflight + `dotenv -e .env.local -- eoas publish`) and never bare `eoas`, because `eoas` runs `expo export` with `EXPO_NO_DOTENV=1` — a direct call inlines `undefined` for all nine `EXPO_PUBLIC_*` values the bundle reads and silently ships an app with no backend. xprem's Postgres must be a **separate database** from the app's Supabase one: it migrates itself on boot and would otherwise drop its tables into the same `public` schema that `db/schema.sql` and `generate_typescript_types` describe. See `docs/ota-self-hosted.md` and the `ota-updates` skill.

## Commands

There is no unit-test suite or linter configured in this project — do not invent `npm test`/`npm run lint` commands. There IS a type checker: run `yarn typecheck` (`tsc --noEmit`) after changes. For on-device verification there are Maestro E2E flows (load the `maestro-e2e` skill).

```bash
yarn start           # expo start
yarn android         # expo run:android (local dev-client build)
yarn ios             # expo run:ios (local dev-client build)
yarn web             # expo start --web
yarn typecheck       # tsc --noEmit
yarn ota:publish     # publish an OTA update to the self-hosted xprem server
```

The first four are the plain Expo commands with `cross-env DISABLE_CODE_SIGNING=1`
in front (see the `ota-updates` skill); `cross-env` is there because inline
`FOO=1 cmd` is a parser error in PowerShell. Never run `eas update` or `npx eoas publish` directly; `yarn ota:publish`
is the only safe publish path.

GitHub Actions (`.github/workflows/`): `ci.yml` typechecks every PR and push to `main`; `ota-publish.yml` runs `yarn ota:publish` to the `preview` branch on every push to `main`, and to `production` when a release tag `v<app version>-ota.<n>` (e.g. `v1.4.0-ota.1`) is pushed — the job checks the tag is on `main` or a `release/*` branch and matches `app.json`'s version (the runtime), and the `production` GitHub environment holds it for a required reviewer's approval and accepts only `main` and those tags. Tags normally go on `main`; once `main` is bumped to a new native version, fixes for the previous store version go on a `release/<old version>` branch cut from its last tag, are tagged there, and are cherry-picked to `main`; manual dispatch (either branch, any platform) stays for hotfixes and rollbacks. Never bump `app.json`'s version to tag an OTA release — that changes the runtime and strands every installed binary; `eas-build.yml` queues EAS builds by manual dispatch (needs an `EXPO_TOKEN` secret). The OTA job pulls the bundle-time `EXPO_PUBLIC_*` values from the matching EAS environment (`eas env:pull` into `.env.local`), so EAS is their single source of truth for CI; GitHub holds only `EXPO_TOKEN`, `XPREM_BASE_URL` (eas-cli evaluates `app.config.js` before it can pull) and `EOO_TOKEN` (the xprem upload credential, deliberately not on EAS). A new `EXPO_PUBLIC_*` value goes in `.env.local` (local publishes and dev) and the EAS environments.

**DB schema changes go through versioned migration files** — write a new `supabase/migrations/<YYYYMMDDHHMMSS>_<name>.sql`, apply it with the Supabase MCP `apply_migration` (same name, exact file contents), and update `db/schema.sql` to keep it an accurate description of the current schema. Never run ad hoc DDL via `execute_sql` or the dashboard SQL editor — the repo folder mirrors the live `supabase_migrations.schema_migrations` history and must stay in lockstep (see `supabase/migrations/README.md`, including the CREATE-OR-REPLACE-preserves-ACLs gotcha that once let function grants drift).

The project is TypeScript-only (`strict: true`, `tsconfig.json` extends `expo/tsconfig.base`; NativeWind `className` props are typed via `nativewind-env.d.ts`). `src/lib/database.types.ts` holds Supabase-generated DB types — regenerate via the Supabase MCP (`generate_typescript_types`) after schema changes; `src/lib/queries.ts` and `src/contexts/auth-context.tsx` derive their row types (`CatalogFragrance`, `TopWornFragrance`, `UserFragrance`, …) from it via the `Tables<"...">` helper. Note: `@rneui` icon-prop typings clash with React 19 types — pass `@expo/vector-icons` elements (e.g. `icon={<FontAwesome .../>}`) instead of `{ name, type }` icon objects.

The project is on Expo SDK 57 (`react-native` 0.86, React 19.2). Google Sign-In requires a real dev-client build (`expo run:ios`/`run:android`) rather than plain Expo Go — Expo Go's fixed identity (`host.exp.exponent`) can't satisfy the OAuth redirect URI registered for this app's real bundle ID (`com.korchev.fragrancecollection`).

## Architecture

### Source layout

All source lives under `src/` (`src/app` is auto-detected by Expo Router). Folder and file names are lowercase kebab-case. Imports across folders use the `@/` alias (`@/* → ./src/*`, defined in `tsconfig.json` `paths`; Metro resolves it natively) — same-directory imports stay relative (`./delete-bottom-sheet`). Static assets (`assets/`, referenced by `app.json`) and `db/schema.sql` stay at the repo root.

### Routing (`src/app/` — Expo Router, file-based)

Root layout (`src/app/_layout.tsx`) wraps the tree in `Sentry.ErrorBoundary > QueryClientProvider > ToastContextProvider > AuthProvider > ThemeContextProvider > LocaleContextProvider`, then renders `<Stack.Protected guard={!!user}>`/`guard={!user}` to switch between `(tabs)` and `sign-in` — this replaces what used to be a manual `user ? <Tabs/> : <SigninScreen/>` check. It also holds an `authLoading` gate (see `src/contexts/auth-context.tsx`) that renders nothing until the initial `supabase.auth.getSession()` resolves, to avoid a sign-in-screen flash on cold start. The native splash screen stays up (`expo-splash-screen`'s `preventAutoHideAsync()`) for that same window — until `authLoading` resolves — instead of auto-hiding onto the blank `return null`. If startup genuinely stalls (>8s) or `getSession()` itself throws (`authError`/`retryAuthInit` on `AuthContext` — previously an unhandled rejection that hung `authLoading` forever), `src/components/startup-recovery.tsx` replaces that blank window with a themed retry screen.

**Headers are the platform's own native-stack headers** — each tab (`(discover)`, `(collection)`, `(profile)`, `(search)`) has its own nested `<Stack>`, and every Stack (those four plus the root one for pushed screens like `wear-history.tsx`/`badges.tsx`/`user-profile.tsx`/`blocked-users.tsx`/`privacy-policy.tsx`/`terms.tsx`) takes its `screenOptions` from `useNativeHeaderOptions()` (`src/lib/utils/use-native-header-options.ts`): page-colored, no hairline, ink title/tint, minimal back button. Tab roots add `headerLargeTitle: true` (iOS large titles; Android shows its Material toolbar), and trailing actions go in `headerRight` (Profile's Settings gear, `user-profile.tsx`'s overflow `NativeMenu`) so iOS 26 renders them as Liquid Glass bar buttons. Titles come from each screen's `options.title`. There is no custom header component any more, and no theme toggle in the header (that's the Appearance menu on the Settings screen). The root layout renders `expo-status-bar` keyed to the in-app theme, since the native header doesn't follow it. Expo Router blocks direct `@react-navigation/*` imports as of SDK 56+; use the `expo-router/react-navigation` and `expo-router/js-top-tabs` re-exports instead.

Sections inside a tab use an iOS `SegmentedControl` (one control row under the title) rather than nested top tabs — Discover's Top / For You is the pattern; secondary choices within a view go in `NativeMenu` dropdowns (`MenuChip` triggers), not more tab rows. Labels come from each screen's `options.title`, not the route name.

**NativeTabs tradeoffs accepted in this app**: a single `tintColor` (no separate configurable inactive-tab color), no custom `tabBarStyle` (native OS chrome instead — iOS liquid glass / Android Material 3), and icons limited to what NativeTabs can render — SF Symbols/Material Symbols/static images/vector-icon-library glyphs, never arbitrary React components (all three tabs currently use `NativeTabs.Trigger.Icon sf=... md=...` system symbols; the old pre-rasterized `assets/collection-icon.png` is no longer referenced).

### Provider stack

- **`src/contexts/auth-context.tsx`** (`useAuth`) — owns Supabase auth state (`user`, `authLoading`; the Google `id_token`/Apple `identityToken` are each exchanged via `supabase.auth.signInWithIdToken`), and is the sole owner of all *write* operations for a user's collection: `addFragranceToCollection`, `requestDelete`/`cancelDelete` (deferred delete with toast-undo window), `updateFragrance` (also accepts `rating`/`notes`), `incrementWear` (calls the `increment_wear` RPC — atomic counter + `last_worn` stamp + a `wear_events` log row for the Most Worn leaderboard, invalidating the `["top-worn"]`/`["wear-history"]` queries; **one wear per calendar day** — the RPC takes the device timezone from `src/lib/utils/worn-today.ts` and returns `false` when today's wear already happened, which surfaces as a toast; wear buttons dim via `isWornToday`; a successful wear shows a toast with an **Undo** action wired to `undoWear`, which calls the `undo_wear` RPC — a mistap would otherwise cost the whole calendar day), `deleteAccount` (invokes the `delete-account` edge function, then signs out locally — the server-side session is already gone with the deleted user). It also owns the other user-initiated writes — `rateFragrance` (upsert into `fragrance_ratings`), `addManualFragrance`, the report/review mutations (`reportFragrance`/`reviewFragranceReport`, `reportProfile`/`reviewProfileReport`, `reviewSubmission`), `blockUser`/`unblockUser` — and the `isPro` flag (RevenueCat `CustomerInfo` listener). The collection *read* is a TanStack query (`["collection", user.id]`); writes and Supabase Realtime `postgres_changes` events both invalidate it — do not rely on Realtime alone for UI freshness. Exposes `userCollection` (raw), `sortedCollection` (sorted by `times_worn`), `visibleSortedCollection` (minus rows pending deletion — screens should render this one), and `collectionPending`/`collectionError` for loading/error UI. The Supabase user object is shimmed with a `photoURL` field (from `user_metadata.avatar_url`) for the Profile tab's Avatar. Also owns the picker state (the picker UI lives at `src/app/picker.tsx`, a modal opened from the Collection tab's FAB): `frag`/`setFrag`/`index`/`getNewFrag` (operating over `pickerPool` — `userCollection` narrowed by the Pro-only `pickerFilters`/`setPickerFilters` — and weighted via `src/lib/utils/pick-weighted-index.ts` — inverse `times_worn`, ~85% downweight for anything worn in the last 24h; `last_worn` is an ISO string, `new Date(...)` it before math). `wear_events.user_fragrance_id` links each event back to the collection row that produced it (`ON DELETE SET NULL`, so leaderboard history survives row deletion) — `undo_wear` uses it to find "today's" event precisely.
- **`src/contexts/toast-context.tsx`** (`useToast`) — bottom snackbar (`showToast({ message, actionLabel, onAction })`), used for the delete/wear undo flows and the gamification/recap toasts. Sits above `AuthProvider` so any context/screen can use it.
- **`src/contexts/locale-context.tsx`** (`useLocale`) — i18n: `t(key, params)` plus locale-aware `formatNumber`/`formatDate`, over `src/lib/i18n/` (`translate.ts` does lookup, `{{param}}` interpolation, and `Intl.PluralRules` plurals). The app ships **English only** (`src/lib/i18n/locales/en.ts`) with no locale picker; screen copy goes through `t()` rather than inline strings so adding a locale later is a dictionary-only change — put new user-facing copy in `en.ts`. Every screen and component now reads its copy through `t()` (the CSV export's column headers are file format and stay literal; `app-crash-fallback.tsx` stays context-free on purpose). It's the innermost provider, so `AuthContext` and plain helpers (`entitlements.ts`, `startup-recovery.tsx`) use `translateDefault` from `translate.ts` instead.

### Data fetching (TanStack Query — there is no DataContext)

All reads go through TanStack Query (`@tanstack/react-query`; client in `src/lib/query-client.ts`, 5-min staleTime; `onlineManager` is wired to `@react-native-community/netinfo` so queries pause offline and refetch on reconnect, and `focusManager` is wired to `AppState` so returning to the foreground refetches stale queries). Shared hooks live in `src/lib/queries.ts`: `useRecommendations(userId, collectionReady)` (the single `recommend_fragrances` RPC, gated until collection startup resolves to avoid a duplicate cold request, with a six-hour cache invalidated by relevant collection/wear/rating writes), `useTopWorn(period)` (community Most Worn leaderboard via the `top_worn_fragrances` RPC; `period` is a `WEAR_PERIODS` key — day/week/month/year/all; every period counts `wear_events` (`'all'` is just unbounded), so wears survive collection-row deletion), `useWearHistory(userId)` (latest 500 raw wear events — only for recent-window readers: heatmap, this-month stat, monthly recap), `useWearSummary(userId)` (uncapped per-scent aggregate via the `wear_summary` RPC — the source for badges, streaks and all-time totals), `useWearDiary(userId, filters)` (the paged, server-filtered diary behind `wear-history.tsx`), `useFragranceSearch(term, filters)` (the `search_fragrances` RPC; enabled once `term` ≥ `MIN_SEARCH_LENGTH` **or** the brand filter is set — browse mode; the search screen debounces input with `useDebouncedValue` from `src/lib/utils/use-debounced-value.ts` and uses `placeholderData: keepPreviousData` to avoid flicker), `useBrands()` (brand facet list for the filter picker via the `list_brands` RPC, 24h staleTime, filtered client-side), `useRemindersEnabled(userId)` (`false` with no `user_push_tokens` rows, otherwise `true` only if every row has `reminders_enabled`), `useNotificationPermission()` (this device's OS permission, `staleTime: 0` so returning from Settings re-reads it — the profile's reminder toggle reads on only when both are true), community data (`useFragranceRatings(ids)` batched averages, `useMyRating`/`useMyRatings`, `useFragranceVoteSummary`/`useFragranceVoteMutation`), profiles (`useMyProfile`, `usePublicProfile`, `useTopCollectors`, `useUserTopWorn`, `useBlockedUsers`), `useStreakSaves`, `useWearHistoryExport`, `useWishlist`/`useWishlistToggle`, and the moderator queues (`useIsModerator`, `usePendingSubmissions`, `usePendingFragranceReports`, `usePendingProfileReports`). Hooks that derive app state from several queries (gamification, onboarding, streak saver, profile sync) live in `src/lib/utils/use-*.ts`. The detail sheet at `src/app/fragrance-detail.tsx` (presented as a `formSheet` from the root Stack) is display-driven from route params, but when opened with a collection row's `id` param it also resolves the live row from `AuthContext.userCollection` — that's what unlocks the editable personal rating/notes and keeps wear stats fresh after a wear. The collection query lives inside `AuthContext` (needs `user.id` + write invalidation). `EmptyState` (`src/components/shared/ui/empty-state.tsx`) is the shared empty/error placeholder (icon + message + optional action) — use it for new empty lists or failed queries instead of ad hoc `<Text>`. When adding a new data source, add a hook to `src/lib/queries.ts` rather than fetching in components or creating a new context; queryFns must `throw` on failure so react-query surfaces `error`.
- **`src/contexts/theme-context.tsx`** (`useTheme`) — light/dark theme. The palette is deliberately hueless (iOS-native greys plus ink — black actions on light, white on dark; `src/design-system/tokens.ts` is the single source of truth): color in the UI comes from the bottle photos, not from an accent hue. Accent and highlight are separate roles that currently both resolve to ink. Precomputes plain-string class groups (`headerColors`, `viewColors`, `cardColors`, `modalColors`) plus `baseColors`/`baseTextClass`/`baseBorderClass` that components destructure and interpolate into `className` strings. **Important**: NativeWind's class scanner only picks up complete literal class-name strings appearing in source — a runtime-built string like `` `text-${baseColors}` `` (where `baseColors` is a bare variable) will NOT work, even though it's valid JS. Always use the precomputed `baseTextClass`/`baseBorderClass` fields (or add a new literal-branch field here) instead of interpolating a bare color name into a class string.

`AuthContext` uses `useQueryClient()`/`useQuery()` internally, so `QueryClientProvider` must stay above `AuthProvider` in the tree.

### Styling

NativeWind v4 (`className` props, Tailwind v3 config in `tailwind.config.js`) — not `tailwind-rn`. Colors referenced outside of `className` (icon `color` props, RN style objects for things Tailwind can't express like `shadowColor`/`shadowOffset`) use `getColor("green-500")` from `src/lib/utils/colors.ts` (a thin wrapper over `tailwindcss/colors`). Third-party UI components from `@rneui/themed` (ListItem, Chip, SearchBar, BottomSheet, Avatar) generally do **not** support `className` on their style-like props (`containerStyle`/`buttonStyle`/`titleStyle`/etc.) — pass real RN style objects (via `getColor()` for theme-driven colors) there instead, not `{ className: "..." }` (that silently no-ops).

Generic, non-domain-specific UI primitives (`Button`, `IconButton`, `TextField`, `SearchField`, `FilterChip`, `SegmentedControl`, `Dialog`, `Row`, `RowGroup` — grouped settings-style rows, `StatTile`, `Badge`, `EmptyState`, `PressableScale` — spring press-scale feedback wrapper used by `IconButton` and `Card.ActionPill`, `SkeletonList` — pulsing card-shaped loading placeholders used instead of `ActivityIndicator` on list screens, `NativeMenu` — the platform's own pop-up menu anchored to a trigger (`@expo/ui`'s `MenuView`: SwiftUI `Menu`, Liquid Glass on iOS 26 / Material 3 `DropdownMenu` on Android), use it instead of `Alert.alert` button lists or ad hoc picker dialogs (items take `checked` for single-choice menus like sort order or appearance; the trigger must not be pressable itself), `GlassCircle` — non-pressable Liquid Glass icon circle (`expo-glass-effect`, falls back to a class background) for use as a `NativeMenu` trigger; both packages are native modules, so a fresh checkout needs a dev-client rebuild) live in `src/components/shared/ui/` (each with a `.stories.tsx`) and are re-exported from its `index.ts` barrel (`import { Button } from "@/components/shared/ui"`, or import a single file directly — both work). Reach for these before hand-rolling a new bordered row, filled/bordered/tinted button, or themed text input — check `src/components/shared/ui/` first. This is separate from `src/components/card.tsx`'s `Card.*` compound components, which stay domain-specific to fragrance list rows (see "Data model conventions" below) — don't move those here, and don't build generic primitives inside `card.tsx`.

### Data model conventions

- Postgres layout (see `db/schema.sql`): `user_fragrances` for a user's collection (`id`, `user_id`, nullable `fragrance_id` FK to the catalog — populated for adds from search/leaderboard, null for legacy rows and manual adds, `name`, `image_url`, `times_worn`, `last_worn`, personal `rating` (1–5, nullable — only used for manual adds; catalog-linked bottles are rated in `fragrance_ratings`) and `notes` (≤2000 chars, nullable — user-entered, edited on the detail sheet), `tags` (free-form personal tags: lowercase, 1–24 chars, ≤12 per row, enforced by the `valid_tag_array` CHECK and mirrored in `src/lib/utils/tags.ts`; edited via `src/components/tag-input.tsx`, used by the Collection tab's tag filter and the Pro picker/history filters), `created_at`), RLS-scoped to `(select auth.uid())`; `wear_events` for the immutable per-wear log (denormalized `name`/`image_url` snapshots so leaderboard history survives collection-row deletion, plus `user_fragrance_id` — `ON DELETE SET NULL` — linking back to the originating row so `undo_wear` can find "today's" event precisely; own-rows RLS — cross-user aggregation only via the `top_worn_fragrances` SECURITY DEFINER RPC, `EXECUTE` revoked from `anon`).
- `name` is stored as a single `"Brand - Title"` string and split on `" - "` at render time (see `src/components/collection-list-item.tsx`, `src/components/top-list-item.tsx`) rather than stored as separate fields — keep this convention when adding new fields/components that display fragrance names.
- List item components (`src/components/collection-list-item.tsx` for the user's collection, `src/components/top-list-item.tsx` for search/leaderboard results) are intentionally separate compositions rather than a single parametrized component — the two contexts have diverging fields (`place`/`wearCount` vs. `timesWorn`/`lastWorn`) and actions (add vs. wear/delete). Both are built from the shared compound-card primitives in `src/components/card.tsx`: `Card.Root` (plain row, or swipeable when given `swipeActions`), `Card.Rank` (medal-colored for podium places 1–3), `Card.Thumbnail` (inset rounded 56px tile on a white backing), `Card.Content`, `Card.Title`, `Card.Subtitle`, `Card.WearInfoText` (single muted meta line — personal "Worn 4× · 3 days ago" via `formatRelativeDay` in `src/lib/utils/relative-time.ts`, or `community` prop for "1,234 wears"; appends "★ 4.2 (56)" when given a rating aggregate), `Card.Overlay` (dark bottom scrim pinned over an image — the picker reel's info strip), `Card.ActionPill` (labeled pill for the everyday actions — "Wear" on collection rows, "Add" on search/leaderboard rows; `worn` flips it to a muted "✓ Worn" state, still tappable so the RPC's "already worn" toast fires; `appearance='solid'` for use over imagery like the picker scrim; fires a light haptic on press), and `Card.ActionButton` (icon-only tinted circle — now just the swipe-reveal delete). `Card.Title`/`Card.Subtitle` take a `color` override and `Card.WearInfoText` an `overlay` prop for the white-on-scrim styling inside `Card.Overlay`. Image-URL validation is shared via `getImageSource` in `src/lib/utils/image-source.ts` (used by `Card.Thumbnail` and the picker reel). Keep the split: add new row types as new compositions of `Card.*`, and put new shared card sections in `card.tsx` rather than duplicating layout. Both push `/fragrance-detail` on row press.
